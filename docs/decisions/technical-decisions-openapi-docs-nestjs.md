# Technical Decisions — OpenAPI Documentation for NestJS

_Subprojects in scope:_

- `nestjs-project/` — backend: generates and exposes the OpenAPI specification. All TDs in this document apply here.
- `next-frontend/` — frontend: **no open decision in this document.** TD-02 defines a stable artifact (`openapi.json`) whose consumption by the frontend (TS client codegen) is future work; a dedicated TD will be opened when the frontend effectively integrates the spec.

---

## TD-01: OpenAPI Documentation Tooling

**Scope:** Backend

**Trigger:** Need to document the NestJS REST API via OpenAPI 3.x, with minimal maintenance friction and alignment with the stack already decided (class-validator + class-transformer — phase-02-auth/TD-06).

**Context:** The NestJS 11 project today publishes no API documentation. Earlier decisions fixed `class-validator` + `class-transformer` for validation (phase-02-auth/TD-06) and defined the standard error envelope (phase-02-auth/TD-07). The OpenAPI tooling choice must preserve those decisions — replacing them would cascade over every DTO already implemented in Phase 02. The decorator-program vs type-introspection trade-off is the central axis.

**Options:**

### Option A: `@nestjs/swagger` (official)
- Official NestJS package, based on decorators (`@ApiProperty`, `@ApiResponse`, `@ApiTags`) and an OpenAPI generator from `DocumentBuilder`. Supports a CLI plugin (`nest-cli.json` → `plugins`) that performs **automatic introspection** of DTOs with `classValidatorShim: true`, reducing explicit decorators to a minimum.
- **Pros:** Native integration with `class-validator`/`class-transformer` (already in the stack). Low learning curve for teams using NestJS. CLI plugin eliminates ~80% of boilerplate when configured. Mature ecosystem: embedded Swagger UI, ready JSON/YAML export, out-of-the-box support for auth schemes (Bearer/JWT). Version `@nestjs/swagger ^11` is compatible with the installed `@nestjs/core ^11.0.1`.
- **Cons:** Requires some additional annotation for complex responses, polymorphism, and per-status variations. Spec depends on runtime metadata (decorators) — there is no "pure type-driven" path without the CLI plugin.

### Option B: Nestia (`@nestia/core` + `@nestia/sdk`)
- Alternative type-driven toolkit: generates the OpenAPI from **pure TypeScript types** (preferentially `interface`), with no `@ApiProperty`. Includes client SDK generation and its own validator (`typia`) ~20,000× faster than `class-validator`.
- **Pros:** Zero-decorator for schema. Embedded SDK codegen. Superior runtime performance (typia). Active community, own docs.
- **Cons:** **Conflicts with the stack already decided in phase-02-auth/TD-06 (class-validator + class-transformer):** Nestia's gain requires adopting `typia` as the validator, which is a re-platform — not compatible with keeping `class-validator` in the already-implemented Phase 02. DTOs would need to be rewritten as interfaces. Lower adoption (relative to the official package). New learning curve.

### Option C: Manual OAS authoring (openapi.yaml/json by hand)
- Maintain the `openapi.yaml`/`openapi.json` file versioned and edited by hand, with no automatic generation from code.
- **Pros:** Total control. Spec not coupled to code.
- **Cons:** Manual maintenance diverges from the real code — high risk of stale spec. No automatic drift detection between DTO and contract. Effort proportional to API growth.

**Recommendation:** **Option A (`@nestjs/swagger`)** — it is the only option that preserves the previous decisions (`class-validator` in phase-02-auth/TD-06) without a re-platform; the CLI plugin with `classValidatorShim: true` leverages existing `class-validator` decorators to infer schemas, keeping boilerplate low. Nestia has real technical merit but the cost of migrating the validation stack makes it unfeasible without an upstream decision to supersede TD-06. Manual authoring is discarded.

**Decision:** A (@nestjs/swagger + CLI plugin)
**Libraries:** @nestjs/swagger

**Revisions:**

- 2026-05-12 — Clarifies that the CLI plugin (`classValidatorShim: true`) only covers schema inference for DTOs from `class-validator`; documentation of operations, status-code-typed responses, error contracts (aligned with the envelope from phase-02-auth/TD-07) and examples require explicit decorators (`@ApiOperation`, `@ApiResponse`, `@ApiBody`, `@ApiParam`, `@ApiQuery`, `@ApiExtraModels`). _Rationale:_ the openapi.json generated by the current bootstrap is generic — no parameter details, no return schemas per status, no error contracts — because the installed base relied only on automatic introspection. This revision fixes that enrichment via explicit decorators is part of the chosen Option A, not work outside the TD's scope.

## TD-02: OpenAPI Spec Artifact Strategy

**Scope:** Cross-layer

**Trigger:** Define how the OpenAPI spec is exposed to consumers — humans (interactive exploration) and machines (future FE client codegen).

**Context:** `@nestjs/swagger` (TD-01, Option A) allows two modes of publishing the spec: **runtime** (Swagger UI + JSON endpoint served by the Nest app) and **static artifact** (`openapi.json` file generated in build/script and committed or published in CI). The choice affects how the frontend (future) consumes the contract: if the spec only exists at runtime, codegen requires the API to be up; if it exists as a file, codegen runs offline in any CI. Since `next-frontend` does not yet integrate the spec but will, the decision is cross-layer — the artifact is the contact point between the subprojects.

**Options:**

### Option A: Runtime-only (Swagger UI + JSON endpoint, no file)
- `SwaggerModule.setup('api/docs', app, document)` mounts UI at `/api/docs` and the JSON at `/api/docs-json`. No file is generated/committed.
- **Pros:** Minimal setup (one block in `main.ts`). Spec always reflects the running code — zero risk of drift between file and runtime. No additional build step.
- **Cons:** FE codegen requires the API running at the time (CI needs to start the backend or point to a stable instance). No contract history in PR diffs — schema changes are invisible until someone compares specs at runtime.

### Option B: Static artifact only (generate `openapi.json`, no runtime UI)
- Script `npm run openapi:gen` that instantiates the NestJS app in "build-only" mode, calls `SwaggerModule.createDocument`, serializes `JSON.stringify(document)` into `openapi.json` (or into `<backend-subproject>/openapi.json`) and exits. Runtime UI disabled. File committed or published in CI.
- **Pros:** Versioned contract — changes appear as a diff in PR. FE codegen runs offline. Easier breaking-change auditing.
- **Cons:** No interactive UI for developers and QA. Spec can go stale if the developer forgets to run the script before commit — requires a hook or CI step to guarantee freshness.

### Option C: Both — runtime UI + static artifact
- Keeps `SwaggerModule.setup('api/docs', ...)` at runtime **and** runs an export script to `openapi.json` in build/CI. UI for humans, file for codegen.
- **Pros:** Covers both use cases without compromising either. FE has a stable artifact; devs/QA have interactive UI. Drift between file and runtime detectable via PR diff (an outdated `openapi.json` is a visible diff).
- **Cons:** Two surfaces to maintain (one line of runtime config + one npm script). Marginally more complex than A or B in isolation.

**Recommendation:** **Option C (Both)** — the marginal cost over Option A is just one npm script (~15 lines) and the benefit is a correct foundation for future FE integration (offline codegen) without losing the interactive UI that dev/QA use. Option B alone punishes the development experience in dev/local; Option A alone compromises the future codegen pipeline. Combining them is dominant.

**Decision:** C (Runtime UI + openapi.json exportado)

## TD-03: Production Exposure Policy for Swagger UI

**Scope:** Backend

**Trigger:** Decide whether the interactive Swagger UI is exposed in production (and under what conditions).

**Context:** The Swagger UI in production is useful (living documentation for integrators) but increases the attack surface: it enumerates all endpoints, accepted parameters, response formats — useful for reconnaissance. Today the project has no public API requirement for third parties; it is a platform oriented to its own frontend (`next-frontend`). The decision is policy, not technical — which side of the trade-off to prioritize.

**Options:**

### Option A: Always exposed (all environments, no auth)
- `SwaggerModule.setup` called unconditionally in `main.ts`. `/api/docs` accessible from any origin in prod.
- **Pros:** No conditionals. Documentation always available for eventual integrators.
- **Cons:** Easier reconnaissance for attackers. Public spec may expose internal endpoints not meant for external consumers (admin, debug). Clashes with the defensive posture of Phase 02 (rate limiting, refresh rotation).

### Option B: Only in dev/staging (disabled in prod via env)
- `if (process.env.NODE_ENV !== 'production') { SwaggerModule.setup(...) }` or a dedicated flag `SWAGGER_ENABLED`. In prod, `/api/docs` returns 404. `openapi.json` (TD-02) remains available as an artifact in the repo/CI for whoever needs it.
- **Pros:** Minimizes surface in prod. Does not block legitimate external consumption — the committed file covers that. Aligned with the defensive stance already established (TD-08 phase-02-auth — throttler).
- **Cons:** Devs need to query staging or the committed file to inspect the prod contract. In prod troubleshooting, no clickable UI (need to replicate locally).

### Option C: Always exposed with basic auth in prod
- `SwaggerModule.setup` always called; in prod, extra middleware protects `/api/docs` with Basic Auth (credentials via env). Dev/staging without protection.
- **Pros:** Documentation available for authorized partners in prod. Anonymous attackers cannot enumerate the API.
- **Cons:** Another credential to manage/rotate (more stuff in `.env`). Basic auth is not robust on its own. Adds specific middleware code. For a project with no clear public use case, it is over-engineering.

**Recommendation:** **Option B (Only in dev/staging)** — aligns with the defensive posture already established in Phase 02 and does not compromise legitimate consumers (the `openapi.json` committed in TD-02 fulfills the role of "spec consultable outside the UI"). Reopening as Option A or C is trivial in the future if a public API use case appears.

**Decision:** B (Apenas em dev/staging via env flag)
